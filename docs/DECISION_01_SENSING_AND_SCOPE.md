# DECISION 01 · 感測策略與 Demo 範圍

**狀態** 待決策 · **建立** 2026-09-04 · **建議決策期限** 開發啟動前

這份文件不是規格，是一份給團隊做決定用的意見書。假設讀者沒有讀過先前的討論，所有論點自足。

## 0. 這份文件要決定什麼

兩件事，其他都可以之後再說：

- **決策 A**：Demo 量測什麼？急性事件（跌倒）還是生活能力趨勢（備餐、外出、服藥）？
- **決策 B**：用什麼感測？影像為主，還是實體感測器＋音效辨識為主？

這兩個決定會影響感測器採購、擺位、模型選擇、資料表與 demo 腳本。**越晚決定成本越高**，因為兩條路的程式碼幾乎不重疊。

## 1. 先確認共識：治理架構不變

`docs/00`–`docs/10` 的治理設計是這個專案目前最紮實的部分，本文件**不建議修改其中任何一項**：

- Risk Agent 與 Intervention Agent 分離，Risk 不可直接通知
- Fact / Hypothesis 分層，Hypothesis 可被反駁、有 `next_test`、人工確認後保留原始假設
- Policy Gateway 作為所有外部行動的閘門，LLM 輸出只是輸入之一
- provenance、schema 版本、idempotency、append-only Ledger
- 「缺失必須顯式標註，不能用空值冒充沒有發生」（doc 02 §3、doc 06 §2.3）
- Prompt injection 對策：ASR 內容只是 evidence，工具權限獨立（doc 09 §8）

以下所有討論都在這個架構之內。**這是換感測器與換事件類型，不是換架構。**

## 2. 現況落差

目前 repo 裡有三份東西，對「這個系統在做什麼」的答案不一致：

| 來源 | 主張的量測對象 | 感測方式 |
|---|---|---|
| `care_agent_demo_*.html` | 泛用事件 | 手機鏡頭 + 麥克風 + Whisper |
| `docs/00`–`10` | impact、floor posture、scream/yell、夜間離床 | Frigate + VLM + ASR |

```
冰箱 0    IADL 0    量表 0    失能 0    備餐 0

長照 2  ← 兩次都在標題「AI 長照 Agent OS」裡
```

這不是誰寫錯了。`docs/` 從工程可行性與安全治理出發，寫得很好；`SPEC.md` 從長照場域定位出發。兩邊各自成立，但**必須收斂成一個 demo**。

## 3. 決策 A：量測什麼

### 選項

| | A1 急性事件 | A2 生活能力趨勢 | A3 雙軌 |
|---|---|---|---|
| 事件 | 跌倒、撞擊、呼救、夜間離床 | 備餐、外出、服藥、洗衣 | 兩者 |
| Demo 表現 | **現場演得出來**，任何人都看得懂 | 需要數月資料，現場只能放模擬 | 一個 live 一個模擬 |
| 差異化 | 弱。市面上跌倒偵測產品很多 | **強。目前沒有同類產品** | 強 |
| 實作成本 | 低（docs 已規劃） | 中（需定義指標與彙總） | 中 |

### 兩者的真實差異

急性軌回答「**現在有沒有出事**」，趨勢軌回答「**這個人這幾個月是不是在退化**」。

長照領域的實際痛點偏向後者：失能評估目前靠專業人員定期到宅、以問答方式填寫量表。而問答式評估在方法學上不適合取得趨勢——量表會問「過去三個月食慾是否減少」，但答案來自受訪者一個瞬間的回憶，而回憶正是認知功能下降者最不可靠的能力。

連續行為觀測正好補這個洞。

### 建議：A3，差異化押在趨勢軌

架構上**已經支援雙軌**——`docs/06 Long-term Observer` 就是趨勢軌，baseline 版本化、coverage、Hypothesis 契約都寫好了。

但有一個實作缺口必須指出：

> **doc 06 是一個設計良好的空容器。** 它定義了 baseline 版本化、coverage、`insufficient_data` 狀態、Finding 契約——全部正確——但從頭到尾沒有定義任何一個 feature。唯一出現的例子是 `night-time exit events`。

`feature definition` 目前是欄位名稱，不是內容。沒有指標清單，Observer 無法實作。這是本專案最大的單一實作缺口，且與感測方式的選擇直接相關。

## 4. 決策 B：用什麼感測

### 選項

- **B1 影像為主**：Frigate + 冰箱鏡頭 + VLM 辨識食材（現行 docs 與 SPEC.md 的共同假設）
- **B2 感測器＋音效為主**：磁簧開關 + 音效事件分類 + 單顆只跑骨架的鏡頭
- **B3 全都要**

### B1 目前面臨的風險

| 風險 | 說明 | fallback |
|---|---|---|
| MiniMax 視覺能力未驗證 | 冰箱食材辨識是核心路徑，但沒測過 | **無**。主辦方只提供 MiniMax，無其他 VLM 可切 |
| Frigate 在 Apple Silicon | Docker Desktop 的 Linux VM 不暴露 Apple GPU／Neural Engine；Coral TPU 的 USB passthrough 在 macOS 上不支援；ffmpeg 拿不到 VideoToolbox 硬解 → 落到 Frigate 官方標示「僅供測試」的 CPU detector | 降 fps 或改原生偵測 |
| 冰箱影像本身 | 內部光線暗、前排遮後排、不透明保鮮盒、拍攝時機（須拍關門前最後一幀，開門瞬間拍到的是上次的狀態） | 補光與差異比對，仍不保證 |
| 會場條件 | 光線與測試環境不同、網路不穩 | 預錄備援 |

**前兩項都沒有備援，而且都在關鍵路徑上。**

### B2 消掉的風險

- **不需要 VLM** → MiniMax 降為「事件序列的語意理解 + 產生報告文字」，純文字任務，能力風險基本消失
- **不需要 Frigate** → 整個 Apple Silicon 部署問題消失
- 磁簧開關幾乎不會失敗，不怕光線、不怕角度
- 音效分類在 Mac mini 上原生跑，Metal 加速

### IADL 覆蓋率比較

反直覺的結果：**覆蓋率變好，不是變差。**

| Lawton IADL 項目 | B1 影像 | B2 感測器＋音效 |
|---|---|---|
| 備餐 | ● 生鮮佔比（依賴 VLM 準確度） | ● 抽油煙機／瓦斯／鍋鏟聲 **vs** 微波爐／電鍋聲的比例 |
| 洗衣 | ○ 拍不到 | ● 洗衣機運轉聲 |
| 外出 | ◐ 玄關鏡頭 | ◐ 磁簧，更可靠 |
| 服藥 | ○ 影像判讀不可行 | ● 藥盒微動開關（單價 10–20 元，一個 GPIO） |
| 購物 | ◐ 冰箱新增品項 | ○ **此項損失** |
| 家務 / 電話 / 理財 | ○ | ○ |

### 一個測量效度上的論點

B1 的備餐判讀是「生鮮佔比下降 → 推論他不下廚了」，這是**間接推論**。
B2 是「抽油煙機這週開六次，上個月十八次」，這是**直接測量烹調行為本身**。

冰箱裡有什麼菜，跟他有沒有真的煮，本來就是兩件事。從構念效度來說，B2 更接近「他還能不能自己煮飯」這個問題。

### B2 的真實損失

必須誠實列出，並從簡報上拿掉或改列 future work：

- **營養面向消失**——蛋白質攝取天數、蔬菜種類數，這些必須看得到內容
- **認知行為代理消失**——重複購買同品項、非食品錯置入冰箱（後者原本是很好的訊號：異常物件偵測比精確盤點容易，臨床意義卻更高）
- **IADL 購物項消失**

未來可用一顆觸發式冰箱鏡頭補回來，不影響現在的架構。

### 建議：B2

最終配置：**磁簧（主）＋ 音效事件分類（主）＋ 單顆只跑 pose skeleton 的鏡頭（急性軌）**

保留那顆鏡頭的理由：

1. 急性軌需要可靠的跌倒偵測。撞擊聲誤報率高（掉東西也是撞擊）
2. 骨架化在 demo 上性價比極高——螢幕上是火柴人在走動，觀眾一眼就懂「沒有在錄他」，把隱私論述視覺化
3. 只跑 pose，**仍然不需要 VLM**

### 資料模型

`docs/04` 的分層不動，新增趨勢層四張表：

```sql
daily_metrics(date, metric_key, value, n_events, coverage)
baseline(metric_key, window_start, window_end, mean, sd, version)
indicator_series(date, instrument, item_code, level, confidence, evidence_json)
assessment_report(id, period_start, period_end, content_json)
```

`notifications` 表補兩個欄位：`recipient_role`、`payload_level`。

理由：`docs/05` 的 L0–L4 是**升級階梯**，不是**收件人路由**，兩者是不同的軸。L3「Caregiver Alert」預設存在 caregiver，但獨居無家屬者沒有；而里長、居服員、照管專員需要不同的資料粒度——長輩的健康狀況屬個資法特種個資，里長不是醫事人員也不是社工師，沒有專業保密義務。

### 音效分類器

不用硬套 YAMNet，自錄樣本訓練小分類器更可控：

```
10 類：抽油煙機 / 瓦斯點火 / 鍋鏟碰撞 / 切菜 / 微波爐嗶 /
      電鍋跳起 / 洗衣機 / 水流 / 沖馬桶 / 撞擊
每類 50–100 樣本 → 梅爾頻譜 + 小 CNN
Mac mini 原生跑，Metal 加速
```

多聲源混合（電視＋洗衣機）是真實限制。Demo 環境可控，但簡報須誠實說明場域準確率會下降。

### ASR 範圍（獨立於本決策，建議一併處理）

目前 ASR 被當成常駐模態 worker。若麥克風 24/7 開著並產生逐字稿，訪客與電話另一端的人會被逐字記錄，而他們從未同意。

建議收窄：

```
對話窗內（系統主動說話後 30–90 秒）→ 啟動 ASR，用完即刪，不落 SQLite
對話窗外                          → 只保留 VAD 布林值 + 音效事件標籤，不啟動 ASR
```

雙向對話功能完整保留，但系統只聽得懂它自己問的問題的答案。這句話可以寫進簡報，而且是真的。

## 6. Demo 分工

會場噪音會殺死 live 音訊 demo，這是 B2 最大的實務風險。

| 模態 | 形式 | 理由 |
|---|---|---|
| 磁簧（開冰箱、開藥盒） | **Live** | 不怕噪音、不怕光線，比攝影機 live 更穩 |
| Pose skeleton | **Live** | 現場走幾步即可 |
| 音效事件辨識 | **預錄** | 會場太吵。微波爐嗶聲辨識度高可試現場，但須有備援 |
| 趨勢曲線與報告 | **模擬資料** | 現場跑不出數月 |

哪些是實作的、哪些是模擬的，簡報須主動說明，不要讓評審自己發現。

## 7. 若不採納 B2

若團隊判斷影像方案的展示效果不可放棄，最低限度應做兩件事：

1. **第一天用 20–30 張真實冰箱照片測 MiniMax 的辨識品質**，並預先決定四層降級：品項可辨識 → 只做差異比對 → 只做粗分類（生鮮／即食／飲品）→ 只用開門事件不看內容
2. **第一天實測 Frigate 在這台 Mac mini 上的 CPU 偵測吞吐量**，確認幾路攝影機、幾 fps 可用

保底敘事在任何情況下都成立：**即使辨識全部失效，開門日誌永遠是準的**，而它就是進食節律的核心訊號。這條讓 demo 不會有單點失效。
